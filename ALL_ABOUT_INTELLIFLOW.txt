1. PROJECT TITLE
IntelliFlow AI – Enterprise Task Management Workspace & AI Knowledge Intelligence Engine

2. PROJECT OVERVIEW
IntelliFlow AI is a high-concurrency, enterprise-grade business operations platform. It unifies project workflow tracking (Kanban boards, task dependencies, activity audits) with an automated Document Management Vault and a grounded Retrieval-Augmented Generation (RAG) knowledge copilot. It is architected as a decoupled hybrid system: a Java 21 Spring Boot 3.2 core transaction engine and a Python 3.12 FastAPI AI microservice with PostgreSQL 16 (pgvector extension) and Redis.

3. WHAT IS INTELLIFLOW?
IntelliFlow is a unified SaaS ecosystem that bridges enterprise task execution with corporate document intelligence. Rather than treating tasks and company documentation as separate silos, IntelliFlow allows employees to upload corporate documents (PDF, DOCX, TXT, Markdown) and interact with an AI Copilot that delivers answers backed by 1:1 verifiable source citations mapped directly to underlying document chunks.

4. PROBLEM STATEMENT
Modern mid-sized organizations face two core productivity bottlenecks:
a. Information Silos: Employees lose up to 20% of their working hours searching through fragmented documentation, scattered task comments, and policy manuals.
b. AI Hallucination & Security Risks: Standard off-the-shelf commercial LLMs lack internal corporate context and hallucinate operational procedures, while sending proprietary corporate data to untrusted third parties violates compliance mandates.

14. POSTGRESQL & RELATIONAL DESIGN
PostgreSQL 16 serves as the unified relational and vector database. ACID compliance guarantees transactional integrity across users, tasks, and document metadata.

15. PGVECTOR EXTENSION
Utilizes pgvector 0.5+ to store high-dimensional embeddings directly in PostgreSQL using the native `vector(384)` data type. Enables unified relational queries joining document metadata with vector cosine distance calculations.

16. REDIS ARCHITECTURE
Used for low-latency session caching, refresh token rotation validation, token revocation blacklisting, and IP-based rate limiting. If Redis is unavailable, the application safely degrades to in-memory caching.

17. AUTHENTICATION (AUTHENTICATION ENGINE)
- Dual-Token Architecture: Short-lived Access Tokens (15 minutes) and long-lived Refresh Tokens (7 days).
- Token Signing: HMAC-SHA256 (or RS256 asymmetric keys) with 256-bit entropy secrets.
- Password Hashing: BCrypt with work factor cost 12 to defend against GPU brute-force attacks.
- Account Lockout: Enforces 5-attempt threshold with a 15-minute cooldown.

18. AUTHORIZATION & ACCESS CONTROL
- Role-Based Access Control (RBAC): ADMIN (full platform control), MANAGER (departmental task and document oversight), MEMBER (assigned tasks and read access).
- Attribute-Based Access Control (ABAC): Document and vector retrieval queries filter strictly by department_id to prevent cross-department data leaks.

19. DOCUMENT VAULT
Centralized document management repository providing file storage, metadata tracking, SHA-256 deduplication, chunk visualization, and processing lifecycle status (UPLOADED -> PARSING -> CHUNKED -> EMBEDDED -> ACTIVE).

20. DOCUMENT UPLOAD PROCESS
1. User uploads file via multipart/form-data.
2. File bytes are buffered into memory.
3. Checksum is calculated and matched against existing database records.
4. If unique, document entity is persisted and dispatched to the ingestion pipeline.

21. SHA-256 DEDUPLICATION
Computes `hashlib.sha256(file_bytes).hexdigest()`. If an identical file is uploaded twice, the duplicate is detected immediately, preventing redundant vector indexing and saving storage.

22. TEXT EXTRACTION ENGINE
Supports multiple file formats without external heavyweight OCR servers:
- PDF: PyMuPDF (fitz) opens in-memory byte streams and extracts structured text page-by-page.
- DOCX: Direct XML parsing of `word/document.xml` using ElementTree, extracting paragraph (`<w:p>`) and text (`<w:t>`) nodes.
- Plaintext / Markdown: Direct UTF-8 decoding with Latin-1 error fallback.

23. TEXT CHUNKING ENGINE
Implements a sliding-window chunking algorithm:
- Chunk Size: 500 words / tokens.
- Chunk Overlap: 50 words / tokens.
- Purpose of Overlap: Preserves semantic context and prevents sentence fragmentation across chunk boundaries.

24. EMBEDDING GENERATION
Dense vector embeddings are generated locally using HuggingFace PyTorch models. Text chunks are encoded into 384-dimensional dense float arrays.

25. ALL-MINILM-L6-V2 MODEL
`sentence-transformers/all-MiniLM-L6-v2` is selected for its high semantic accuracy, compact 384-dimensional output, and low CPU latency (<20ms per passage).

26. 384-DIMENSIONAL VECTOR MATHEMATICS
Vectors are normalized to unit length (`normalize_embeddings=True`). On unit vectors, Cosine Distance is directly calculated via the dot product:
Cosine Similarity = dot(A, B) / (|A| * |B|) = dot(A, B).
Cosine Distance = 1.0 - Cosine Similarity.

27. HNSW (HIERARCHICAL NAVIGABLE SMALL WORLD) INDEX
PostgreSQL indexes vector columns using HNSW:
`CREATE INDEX idx_document_chunks_embedding_hnsw ON document_chunks USING hnsw (embedding vector_cosine_ops);`
HNSW creates a multi-layer geometric graph providing logarithmic O(log N) search times, significantly outperforming flat scans and IVFFlat indexes.

28. VECTOR SIMILARITY SEARCH PIPELINE
1. User query text is converted to a 384-dim vector.
2. Query vector is formatted as `[v0, v1, ..., v383]`.
3. SQL query executes cosine distance search (`<=>` operator) against `document_chunks`.
4. Top-K closest passages are returned with similarity scores (`1.0 - distance`).

29. RETRIEVAL-AUGMENTED GENERATION (RAG) PIPELINE
1. User submits a question.
2. Top-K relevant candidate chunks are retrieved from vector store.
3. Citations are extracted with document titles and similarity scores.
4. PromptBuilder injects passages into the LLM system context.
5. LLM generates grounded completion based strictly on retrieved facts.

30. PROMPT CONSTRUCTION & GROUNDING
PromptBuilder formats retrieved chunks as `[Source N: Document Title]
Content` and instructs the model:
- Ground answers strictly on retrieved enterprise knowledge.
- Deliver comprehensive, expert technical explanations for engineering questions.
- Avoid fabricating facts or citing unverified sources.

73. LIKELY INTERVIEW QUESTIONS
1. Why PostgreSQL + pgvector over standalone vector DBs like Pinecone?
2. How does the 50-token chunk overlap prevent context loss?
3. How do you prevent prompt injection and unauthorized cross-department data leakage?
4. What is the mathematical relationship between Cosine Distance and Dot Product on normalized vectors?
5. How does Java 21 Virtual Threads improve backend concurrency?

74. TECHNICAL INTERVIEW ANSWERS
1. PostgreSQL + pgvector unifies relational metadata and vector embeddings in an ACID-compliant engine, eliminating dual-write consistency issues and external egress costs while enabling unified SQL joins.
2. The 50-token sliding-window overlap ensures that sentences or concepts spanning chunk boundaries are not abruptly severed, maintaining semantic continuity during retrieval.
3. Strict ABAC filtering in SQL (d.department_id = :dept_id) enforces tenant isolation before vector sorting, while structured prompt context isolation prevents untrusted document text from altering system instructions.
4. For unit-length normalized vectors (|A| = |B| = 1), Cosine Similarity is identically equal to the dot product (dot(A, B)), and Cosine Distance is 1.0 - dot(A, B), enabling ultra-fast hardware computation.
5. Virtual Threads (Project Loom) map millions of lightweight user-mode threads onto carrier OS threads, allowing high-concurrency blocking I/O without pool exhaustion.
